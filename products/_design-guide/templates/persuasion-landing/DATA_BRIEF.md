# 설득형 랜딩 템플릿 — 제품 데이터 작성 지시

제품마다 `data/<제품 폴더명>.json` 한 개를 만든다. 엔진(`engine.html`)이 이 JSON 하나로 제품 전용 랜딩 템플릿(7개 화면)을 그린다. 완성 예시는 `data/flora-publishing.json`이다. 형식과 문장 톤을 그대로 따른다.

## 근거 문서 (이것만 쓴다)

| 문서 | 가져올 것 |
|---|---|
| `products/<제품>/01_PRD.md` 1장 | 페르소나 3명(상황·목표·좌절), 핵심 과제 |
| `products/<제품>/01_PRD.md` 4장 | 플랜·크레딧·팩 가격(정본). 계산기와 도입 단계는 이 값만 쓴다 |
| `products/<제품>/01_PRD.md` 6장 | 금지 문구(허위 수치, 가상 후기, 보장 표현). 모든 문장이 통과해야 한다 |
| `products/<제품>/03_SCREENS_UX.md` 4절 | 랜딩 브리프(주제, 대상, 주된 일), 헤드라인·카피, 토큰(accent 색 고를 때) |
| `products/<제품>/02_ARCHITECTURE.md`, `06_AGENT_PLAN.md` | 실제 처리 순서(flow)와 증거로 쓸 산출물 |
| `Price_Plans/<제품>/PRICE_PLAN.md` 4장 | 대안(경쟁·대체재)의 범주. 실명은 JSON에 넣지 않는다 |
| `products/_design-guide/LANDING_PERSUASION.md` | 판정표·증거 등급·주장 장부 규칙 |

## 절대 규칙

1. 한국어. 평이한 문장. 문서에 없는 사실·수치·기능을 만들지 않는다. 확인 못 한 것은 "(미확인)".
2. 통계, 사용자 수, 절감률, 후기 같은 숫자를 쓰지 않는다. 가격·크레딧은 01장 4장 값만(제안값이어도 그대로).
3. 대안은 범주 이름만(예: "그대로 둔다", "범용 AI 채팅", "사람에게 맡긴다", "전문 도구"). 회사·서비스 실명과 로고 금지. 범주는 제품에 맞게 바꿔도 된다(4개 고정).
4. 판정표 우리 열에는 △(t) 또는 ✕(x)가 최소 1개. 우리 열이 ○(o)인 행은 마지막 칸(증거 ID)이 비면 안 된다. 증거 ID는 evidence 목록에 있어야 한다("요금" 같은 페이지 이름도 허용).
5. 주장 장부 상태: 페르소나 장면 = "draft"(V0 인터뷰 전), 기능 사실 = "hold"(출시 전), 측정치 = "draft"(측정 전, 숫자 자리는 ○). "ok"는 쓰지 않는다.
6. 페르소나 3명의 `id`는 ledger의 앞 3개 ID와 같아야 하고, `scene` 문장은 ledger 문장과 같아야 한다.
7. A-RMS 벤치마킹 원자료의 문구("이슈 ≠ 요구사항", "끊어진 정보", Time·Scope·Resource 질문 등)를 쓰지 않는다.
8. 의료·법률·투자·운세처럼 판단이 걸린 제품은 보장·단정 표현을 피하고 01장 6장 대체 문구를 따른다.

## 계산기 규칙

"지금 방식 vs 제품" 비교. 사용자가 자기 숫자를 넣는다. 기본값은 "예시"로 표시되므로 그럴듯한 예시면 되지만, 제품 쪽 가격·크레딧은 반드시 01장 4장 값이다. 제품 쪽 "시간 절감"은 사용자가 넣은 값만 쓴다(V1 측정 전).

| 필드 | 형식 |
|---|---|
| title | 계산기 제목 |
| groups | `[[그룹 제목, [[키, 라벨, 단위, 기본값 숫자 또는 선택지 배열]]]]`. 키는 영문 소문자. 선택지 배열의 첫 값이 기본 |
| derived | `[[이름, 식]]` 위에서 아래로 계산되는 중간값(선택) |
| rows | `[[방법 이름, 비용 식(숫자), 시간 식(문자열), 설명 식(문자열)]]` 2~3행. 마지막 행이 이 제품 |
| formula | 계산식 설명 문자열(줄바꿈 \n) |
| note | 빠진 가정·한계 한 줄 |

식은 자바스크립트 표현식이다. 쓸 수 있는 것: 입력 키, derived 이름, `max min ceil floor round`, `won(n)`(원 표기 문자열), `fmt1(n)`(소수 한 자리), `pack(n, [[크레딧,가격],...])`(n 크레딧을 덮는 가장 싼 팩 조합 가격). 문자열 비교는 `===`. 비용 식은 반드시 숫자.

## 끝나면

JSON이 `python3 -c "import json;json.load(open('<파일>'))"`로 읽히는지 확인하고, 마지막 메시지로 파일 경로와 "근거로 쓴 문서·절", "확인하지 못해 미확인으로 둔 것"만 짧게 보고한다.

## 2판 필드 (프로세스 메뉴 템플릿)

2판 엔진은 GNB를 구매 여정 5단계(01 문제 → 02 해결 → 03 비교 → 04 검증 → 05 도입)로, 그 아래 하위 GNB를 단계별 하위 페이지로 그린다. 아래 필드를 추가하면 "핵심 기능", "결과물", "경쟁 지형", "자주 묻는 질문" 페이지가 생긴다. 없으면 그 페이지는 메뉴에서 빠진다. 기존 필드는 그대로 둔다.

| 필드 | 형식 | 설명 |
|---|---|---|
| features | 4~6개 | `{title, icon, sum:한 줄, points:[세부 2~4개], ref:근거 문서·절}`. 01장·03장에 있는 기능만 |
| outputs | 3~5개 | `[결과물 이름, 형식, 설명]`. 사용자가 손에 쥐는 산출물 |
| market | 객체 | `line`(경쟁 지형 한 문장), `lead`(2문장), `axes:{xname, x:[낮은 쪽 라벨, 높은 쪽 라벨], yname, y:[아래 라벨, 위 라벨]}`, `ours:[x, y]`(0~10), `gaps:[[시장 빈틈, 설명]]` 2~3개 |
| competitors | 4~6개 | 아래 경쟁사 규칙 |
| faq | 4~6개 | `[질문, 답]`. 답은 01장 4장·6장과 어긋나지 않게 |

경쟁사 항목: `{name, cat, region:"국내"|"해외", url, price, checked:"YYYY-MM-DD", for:주 사용자, strengths:[2~3], weaknesses:[1~3], vs:우리와 다른 점 한 줄, xy:[x, y], src:[출처 URL 또는 레포 문서 경로]}`

1. `cat`은 alts 4개 범주 이름 중 하나와 정확히 같다(대안 판정표 열과 연결된다).
2. 이름·가격·기능은 공식 페이지나 레포 `Price_Plans/<제품>/PRICE_PLAN.md` 4장에서 확인한 것만 쓰고, 확인한 날을 `checked`에 적는다. 확인 못 한 값은 "(미확인)".
3. 강점은 공정하게 쓴다(2개 이상). 약점은 확인 가능한 사실(지원하지 않는 기능, 플랫폼 제한, 가격 구조, 언어)만 쓰고 평가어("불편하다", "형편없다")를 쓰지 않는다.
4. `xy`는 `market.axes` 기준 0~10 정성 배치다. 화면에 "정성 배치(제안)"로 표시된다. 근거가 약하면 중앙(5) 근처에 둔다.
5. 로고·스크린숏·원문 문구는 쓰지 않는다. 실명 비교 화면은 내부 시안이며 공개 게시 전 비교광고 기준 확인이 필요하다고 화면에 표시된다.
6. 검사는 `node validate.js`로 한다. 마지막 줄이 `ALL OK`여야 한다.

## 3판: 공통 템플릿과 제품 맞춤 여정

새 제품 랜딩은 공통 템플릿에서 시작한다. `data/_common.json`을 `data/<제품>.json`으로 복사해 [ ] 자리를 채우고, `journey`로 여정 이름과 단계를 제품 개발 요건에 맞게 바꾼다. `journey`가 없으면 공통 구매 여정(01 문제 → 02 해결 → 03 비교 → 04 검증 → 05 도입)을 쓴다.

| 필드 | 형식 | 설명 |
|---|---|---|
| title | 문자열(선택) | 페이지 제목. 없으면 "<short> 설득형 랜딩 템플릿" |
| journey | 객체(선택) | `{name:"<제품> ○○ 여정", head, lead, stages}` |
| journey.stages | 3~7개 | `{no:"01", label:2~3자, icon, q:방문자의 질문, ref:근거(예: "J1 · 위저드 1~6단계"), pages}` |
| journey.stages[].pages | 1~5개 | `{id, title, desc, type, pick, range, data, head, lead, ref}` |
| wizard | 객체(선택) | `{title, lead, steps:[{name, icon, user, system, credit, ref}]}`. 순서가 있는 사용 단계(위저드·온보딩) |
| tables | 객체(선택) | `{<키>:{title, lead, cols, rows, note}}`. 에이전트 표, 점검표 같은 제품 요건 표 |

하위 페이지 `type`(없으면 `id`와 같다): scene, cause, flow, steps(`range:[시작, 끝]`, 0부터), features(`pick:[번호]`로 일부만), outputs, market, verdict, nonfit, evidence, ledger, validate, insight, plans, calc, faq, table(`data:"<tables 키>"`).

규칙
1. `id`는 영문·숫자·-·_만 쓰고 여정 안에서 겹치지 않는다. home, guide는 쓰지 않는다.
2. 단계와 하위 페이지는 기획 문서의 핵심 과제·기능 요구사항(01장 1장·3장)과 화면(03장) 순서를 따른다. 각 단계 `ref`에 근거를 적는다.
3. 여정에 넣지 않은 주장 장부·검증 단계는 템플릿 메뉴의 "검증 노트"로 남는다.
4. 데이터에 없는 유형의 페이지는 메뉴에서 자동으로 빠진다.

## 음성 지시 (모든 제품 필수)

모든 제품은 공용 음성 구조(`products/_platform-core/VOICE_ARCHITECTURE.md`, 확정 결정 16: faster-whisper(Whisper) 오픈소스 음성 서버 + ElevenLabs)를 쓴다. 템플릿은 `voice` 필드로 "음성 지시" 페이지와 히어로의 "말로 지시 · Whisper 음성" 표시를 그린다. 공통 규칙(확인 후 전송, 원본 미저장 기본, 첫 사용 고지, 음성 없이도 모든 기능, STT 크레딧)은 엔진이 넣는다.

| 필드 | 형식 | 설명 |
|---|---|---|
| voice.lead | 문자열 | 이 제품에서 말로 할 수 있는 일 한 문장 |
| voice.say | 1~3개 | `[사용자가 말하는 예시, 그 말로 일어나는 일]`. 01장 음성 기능의 실제 동작만 |
| voice.items | 1~4개 | `[기능 이름, 하는 일, 기능 ID]`. 01장 음성 기능 행 |
| voice.rules | 선택 | `[항목, 내용]`. 제품만의 예외(병원 전용 서버, 동의 후 저장 등) |

규칙: 음성으로 할 수 없는 일(매매·주문, 원고 자동 변경 등)은 할 수 있는 것처럼 쓰지 않는다. 음성 답이 원고·데이터를 바로 바꾸지 않는 제품은 그렇게 적는다.
