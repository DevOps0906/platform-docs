# 설득형 랜딩 템플릿 — 제품 데이터 작성 지시

제품마다 `data/<제품 폴더명>.json` 한 개를 만든다. 엔진(`engine.html`)이 이 JSON 하나로 제품 전용 랜딩 템플릿(7개 화면)을 그린다. 완성 예시는 `data/flora-publishing.json`이다. 형식과 문장 톤을 그대로 따른다.

## 근거 문서 (이것만 쓴다)

| 문서 | 가져올 것 |
|---|---|
| `products/<제품>/01_PRD.md` 1장 | 페르소나 3명(상황·목표·좌절), 핵심 과제 |
| `products/<제품>/01_PRD.md` 4장 | 플랜·크레딧·팩 가격(정본). 계산기와 도입 단계는 이 값만 쓴다 |
| `products/<제품>/01_PRD.md` 6장 | 금지 문구(허위 수치, 가상 후기, 보장 표현). 모든 문장이 통과해야 한다 |
| `products/<제품>/03_SCREENS_UX.md` 4절 | 랜딩 브리프(주제, 대상, 주된 일), 헤드라인·카피, 토큰(accent 색 고를 때) |
| `products/<제품>/02_ARCHITECTURE.md`, `06_AGENT_PLAN.md` | 실제 처리 순서(flow)와 증거로 쓸 산출물 |
| `Price_Plans/<제품>/PRICE_PLAN.md` 4장 | 대안(경쟁·대체재)의 범주. 실명은 JSON에 넣지 않는다 |
| `products/_design-guide/LANDING_PERSUASION.md` | 판정표·증거 등급·주장 장부 규칙 |

## 절대 규칙

1. 한국어. 평이한 문장. 문서에 없는 사실·수치·기능을 만들지 않는다. 확인 못 한 것은 "(미확인)".
2. 통계, 사용자 수, 절감률, 후기 같은 숫자를 쓰지 않는다. 가격·크레딧은 01장 4장 값만(제안값이어도 그대로).
3. 대안은 범주 이름만(예: "그대로 둔다", "범용 AI 채팅", "사람에게 맡긴다", "전문 도구"). 회사·서비스 실명과 로고 금지. 범주는 제품에 맞게 바꿔도 된다(4개 고정).
4. 판정표 우리 열에는 △(t) 또는 ✕(x)가 최소 1개. 우리 열이 ○(o)인 행은 마지막 칸(증거 ID)이 비면 안 된다. 증거 ID는 evidence 목록에 있어야 한다("요금" 같은 페이지 이름도 허용).
5. 주장 장부 상태: 페르소나 장면 = "draft"(V0 인터뷰 전), 기능 사실 = "hold"(출시 전), 측정치 = "draft"(측정 전, 숫자 자리는 ○). "ok"는 쓰지 않는다.
6. 페르소나 3명의 `id`는 ledger의 앞 3개 ID와 같아야 하고, `scene` 문장은 ledger 문장과 같아야 한다.
7. A-RMS 벤치마킹 원자료의 문구("이슈 ≠ 요구사항", "끊어진 정보", Time·Scope·Resource 질문 등)를 쓰지 않는다.
8. 의료·법률·투자·운세처럼 판단이 걸린 제품은 보장·단정 표현을 피하고 01장 6장 대체 문구를 따른다.

## 필드

| 필드 | 형식 | 설명 |
|---|---|---|
| key | 문자열 | 제품 폴더명 |
| name, short | 문자열 | 정식 이름, 짧은 이름(메뉴·표 머리에 쓴다, 12자 이하) |
| accent | `#rrggbb` | 어두운 배경에서 읽히는 밝은 강조색. 03장 토큰의 강조색을 밝게(명도 70~80%) |
| pill | 문자열 | 한 줄 분류(20자 안팎) |

| chips | 문자열 3~6개 | 제품이 다루는 대상 이름(짧게) |
| join | 문자열 | chips 뒤에 붙는 짧은 연결어("판형으로", "를 한 번에") |
| head | 문자열 | 히어로 헤드라인. 03장 카피가 있으면 그대로 |
| sub | 문자열 | 2~3문장 설명 |
| cta | 문자열 | 주 행동 버튼 문구(누르면 일어나는 일) |
| formula | 문자열 | "입력 + 입력 = 결과" 한 줄 |
| personas | 3개 | `{who:"이름 · 나이 · 역할", icon, cap:짧은 캡션, sit:상황, scene:막히는 장면 한 문장, want:원하는 것, id}` |
| cause | 객체 | `line`(원인 한 문장), `lead`(2문장), `bad`:[제목, 부제], `good`:[제목, 부제], `rows`:[[속성, 기존 방식, 제품 방식]] 4~5개 |
| flow | 4~6개 | `[단계명, icon, 사용자가 하는 일, 승인 여부(true/false), 제품이 하는 일]` 실제 처리 순서 |
| alts | 4개 | `[범주 이름, 부제(없으면 "")]` |
| table | 5~6행 | `[기준, [[mark, 근거]×4 대안], [mark, 근거](우리 열), 증거 ID 또는 ""]`. mark: o 된다, t 일부·조건부, x 안 된다, n 해당 없음 |
| nonfit | 3~4개 | `[이런 경우, 다른 방법]` |
| evidence | 3~5개 | `[ID(<약어>-E-01), 등급(E1~E5), 증거, 조건]`. E1 가입 없이 해 보기, E2 실제 결과 파일, E3 화면 기록, E4 측정, E5 동의받은 사례 |
| ledger | 5~7개 | `[ID(<약어>-C-01), 화면 문장, 유형(문제 묘사·기능 사실·비교·측정치), 증거, 상태]` |
| stages | 2~4개 | `{label, price, per, steps:[[사용자가 하는 일, 제품이 해 주는 일]]}` 01장 4장 요금 구조 순서 |
| calc | 객체 | 아래 계산기 규칙 |
| insight | 0~3개 | `[글 제목, 다루는 것, 판정 기준]`. 즉시 가입형·설치형 등 논증 글이 맞지 않으면 `[]` |

## 계산기 규칙

"지금 방식 vs 제품" 비교. 사용자가 자기 숫자를 넣는다. 기본값은 "예시"로 표시되므로 그럴듯한 예시면 되지만, 제품 쪽 가격·크레딧은 반드시 01장 4장 값이다. 제품 쪽 "시간 절감"은 사용자가 넣은 값만 쓴다(V1 측정 전).

| 필드 | 형식 |
|---|---|
| title | 계산기 제목 |
| groups | `[[그룹 제목, [[키, 라벨, 단위, 기본값 숫자 또는 선택지 배열]]]]`. 키는 영문 소문자. 선택지 배열의 첫 값이 기본 |
| derived | `[[이름, 식]]` 위에서 아래로 계산되는 중간값(선택) |
| rows | `[[방법 이름, 비용 식(숫자), 시간 식(문자열), 설명 식(문자열)]]` 2~3행. 마지막 행이 이 제품 |
| formula | 계산식 설명 문자열(줄바꿈 \n) |
| note | 빠진 가정·한계 한 줄 |

식은 자바스크립트 표현식이다. 쓸 수 있는 것: 입력 키, derived 이름, `max min ceil floor round`, `won(n)`(원 표기 문자열), `fmt1(n)`(소수 한 자리), `pack(n, [[크레딧,가격],...])`(n 크레딧을 덮는 가장 싼 팩 조합 가격). 문자열 비교는 `===`. 비용 식은 반드시 숫자.

## 끝나면

JSON이 `python3 -c "import json;json.load(open('<파일>'))"`로 읽히는지 확인하고, 마지막 메시지로 파일 경로와 "근거로 쓴 문서·절", "확인하지 못해 미확인으로 둔 것"만 짧게 보고한다.
