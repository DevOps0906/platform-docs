# 09 랜딩페이지 기획: 벤치마킹과 구조 (v2)

작성일 2026-10-20. v1 랜딩(캔버스 첫 안)은 "사진이 주인공"이라고 해 놓고 사진 자리가 빈 회색 상자였고, 지도 일러스트와 본문 사이에 연결이 없었다. 이 문서는 비슷한 플랫폼을 조사해 구조부터 다시 잡는다. 시각 값은 `08_DESIGN_SYSTEM.md`를 따른다.

## 1. v1이 별로였던 이유 (진단)

| 문제 | 원인 | 고칠 방법 |
|---|---|---|
| 첫 화면이 "그림 한 장 + 검색"뿐이라 서비스가 뭔지 모른다 | 가치 제안과 신뢰 요소가 히어로에 없음 | 히어로 바로 아래에 신뢰 3줄(총액 먼저, 취소 규정, 호스트 원문) |
| 숙소 카드가 빈 회색 상자 | 사진이 없는 상태로 "사진 중심"을 흉내 냄 | 사진이 들어오기 전까지 브랜드 일러스트 장면 6종을 쓰고, 실제 사진이 오면 교체 |
| 둘러볼 기준이 없음 | 카테고리 탐색이 없음 | 아이콘 + 글자 카테고리 줄(바다, 한옥, 숲, 독채, 반려동물, 장기) |
| 가격 비교 가치가 안 보임 | 지도와 목록 관계를 보여 주지 않음 | "지도로 가격 비교" 섹션(목록 + 지도 + 가격 핀) |
| 호스트 섹션이 약함 | 배너 한 줄 | 호스트 전용 구간: AI 도우미 3가지 + 등록 단계 + 사전 신청 |
| 문서에 없는 구성 | FAQ, 정책 안내가 없음 | 예약 방식·취소·호스트 비용 FAQ(값은 확정 전 표시) |

## 3. 핵심 방향 한 줄과 전략

- 방향: **"사진 한 장이 아니라, 호스트가 쓴 그대로를 믿고 고르는 숙소 앱"**. Airbnb의 신뢰 장치(총액·카테고리·사진 격자)는 쓰되 빨강·로고·카드 배치는 쓰지 않는다.
- **공급 먼저**: 마켓플레이스는 숙소가 없으면 게스트도 없다(콜드 스타트). 린 검증 순서에 따라 랜딩의 첫 지표는 예약이 아니라 **호스트 사전 신청 수와 지역 수요 신호(검색어 기록)** 다. 게스트 랜딩과 호스트 랜딩(`/host`)을 분리한다.
- 실제 숙소·후기가 없을 때 가짜 평점·후기를 만들지 않는다. "아직 후기 없음", 샘플은 "예시" 표시.

## 4. 구조 (게스트 랜딩 `/`)

| 순서 | 섹션 | 목적 | 내용 | 측정 |
|---|---|---|---|---|
| 1 | 헤더 | 길 찾기 | 로고, 숙소 찾기·호스트 되기·도움말, 로그인. 스크롤하면 검색 바가 헤더로 축소 | — |
| 2 | 히어로 | 한 문장 가치 + 검색 | 헤드라인 + pill 검색(지역·체크인·체크아웃·인원) + 오른쪽 장면 모자이크(4~5장, 가격 칩) | 검색 시작률 |
| 3 | 신뢰 줄 | Vrbo 약점 방지 | 총액을 먼저 · 취소 규정을 예약 전에 · 호스트가 쓴 정보 그대로 | — |
| 4 | 카테고리 | 목적지 모르는 사람의 길 | 아이콘 줄 7개(전체, 바다, 한옥, 숲, 독채, 반려동물, 장기 숙박) | 카테고리 클릭률 |
| 5 | 추천 컬렉션 | 둘러보기 | 가로 스크롤 카드 6장(장면, 제목, 지역, 총액 예시, 아직 후기 없음) | 카드 클릭률 |
| 6 | 지도로 가격 비교 | 차별점 | 목록 + 지도 + 가격 핀(선택 시 연결) | 지도 보기 전환 |
| 7 | 이용 방법 | 요청 승인제 설명 | 3단계(고르기 → 요청 → 확정) | — |
| 8 | AI 안내 | 신뢰와 편의 | "근거를 보여 주는 AI 답변" 예시 말풍선 + 출처 칩 | — |
| 9 | 호스트 구간 | 공급 확보 | 소개글 초안·자동 답변·음성 등록 3가지 + 등록 흐름 + CTA "사전 신청" | 사전 신청 수 |
| 10 | FAQ | 이탈 방지 | 예약 확정 방식, 취소 규정, 호스트 비용(확정 전 표시) | — |
| 11 | 푸터 | 법적 | 회사 정보, 약관, 개인정보, 환불·취소 | — |

호스트 랜딩 `/host`(다음 작업): 히어로(숙소 올리기) → 3단계 → AI 도우미 → 수수료·정책(확정 전 표시) → 사전 신청 폼. 예상 수익 계산기는 근거 데이터가 확보되기 전에는 만들지 않는다(수익을 보장하는 문구 금지).

## 5. 시각 규칙 (v2)

- 색·서체·간격은 08장 토큰만 쓴다. 노을 주황은 화면당 한 곳(지도 섹션의 선택된 가격 핀).
- 이미지: 실제 사진이 들어오기 전까지 **브랜드 일러스트 장면 6종**(바다, 숲, 한옥, 산, 도시, 노을 들판)을 같은 팔레트로 쓴다. 장면은 평면 도형이고 특정 장소를 흉내 내지 않는다. 사진이 오면 4:3 `photo` 비율로 교체하고 장면은 빈 상태 대체로 남긴다.
- 헤드라인 56/64(모바일 36/44), 섹션 제목 32/40, 카드 제목 body 700. 한 줄 최대 약 65자.
- 간격: 섹션 간 96px(모바일 56px), 카드 간 24px.
- 모션: 카드 호버 확대 1.02 이내, 검색 바 축소 200ms. reduced-motion이면 없음.
- 모바일: 검색은 한 칸으로 접히고 눌러서 시트 열기, 카테고리와 컬렉션은 가로 스와이프, 지도 섹션은 목록 위주.

## 6. 접근성·성능
- 장면 SVG는 장식(`aria-hidden`), 카드 이름이 접근 이름. 카테고리 줄은 `<a>`/`<button>`이며 키보드 가능.
- LCP 후보는 히어로 장면(인라인 SVG, 요청 없음). 실제 사진 도입 시 히어로 1장만 우선 로드.

## 7. 린 검증 (개발 전)
1. 이 랜딩을 노코드로 먼저 게시하고 호스트 사전 신청 폼만 연결한다. 지표: 방문 → 사전 신청 전환.
2. 지역 3곳(예: 제주, 강릉, 양양 — 제안)을 정해 호스트 인터뷰 10명을 목표로 한다(제안).
3. 신청 수가 목표(제안 지역당 20)를 넘으면 개발(W1~)을 시작한다. 정부지원사업 신청서의 시장 검증 근거로도 쓴다.

## 12. v3 개편 (2026-10-20): 히어로 애니메이션 · GNB · 검색 흐름

| 항목 | 내용 |
|---|---|
| 히어로 | 풀폭 무대(라운드 24px) 위에 일러스트 3장면(제주·홍천·전주)이 18초 주기로 크로스페이드, 천천히 확대(켄 번스), 구름 이동, 가격 핀 둥실, 해 빛무리 맥동. `prefers-reduced-motion`이면 정지하고 첫 장면만 고정 |
| 레이아웃 원칙 | 텍스트 카드와 검색 바는 겹치지 않는 세로 플렉스(위: 카드, 아래: 검색 바). 장면은 뒤 레이어. 760px 이하에서 검색 바는 2열로 접힘 |
| GNB | 로고 · [검색] · 숙소 찾기 · 호스트 되기 · 도움말 · 로그인 · 회원가입. **검색 버튼이 숙소 찾기 앞**. 상단 고정(sticky). 위에 환율 띠 |
| 검색 모달 | 히어로 검색 바·GNB 검색·카테고리·숙소 카드 어디서든 열림. 지역(입력+추천 칩), 체크인, 체크아웃(체크인 이후만), 성인·어린이(성인 1명 이상, 합계 최대 16명), 모두 지우기, 검색하기. 빠진 값은 모달 안에서 안내 |
| 다음 화면 | 검색하면 결과 화면으로 이동해 입력한 지역·날짜·박수·인원을 상단에 보여 주고(검색 조건 바꾸기 가능), 카드마다 1박 가격·N박 총액·참고용 환산 표기 |
| 예약 게이트 | 결과 카드의 "예약 요청"을 누르면 "예약하려면 회원가입이 필요해요" 안내. 회원가입 / 로그인 / 나중에. 검색 조건은 가입 후에도 이어지는 것으로 설계(제안) |
| 로그인 없이 | 둘러보기·검색은 비로그인 가능, 예약 요청만 가입 필요 |
| 미확인 | 가입 화면 상세(별도 설계), 어린이 연령 기준, 실제 검색 결과 정렬·필터, 애니메이션 성능(저사양 기기) |

디자인 캔버스에는 홈 프로토타입과 함께 검색 모달, 검색 결과, 예약 게이트 3개 상태 보드를 두었다.

## 13. v4 변경 (2026-10-20): 히어로 검색 제거 · 환율 위치 · 예시 숙소 불러오기 · 챗봇

| 항목 | 내용 |
|---|---|
| 히어로 검색 | 삭제. 검색은 GNB의 [검색] 버튼 하나로 통일 |
| 환율 | 히어로 바로 아래 띠로 이동(검색 결과 화면 상단에도 같은 띠). 값은 예시, 참고용·기준일 표기 |
| 숙소 찾기 / 이번 주 둘러볼 곳 | GNB "숙소 찾기"와 카드 클릭은 검색 모달을 열고 **예시 카드의 정보(지역, 1박 가격 → 최대 예산, 예시 날짜)를 채워서** 보여 준다. 사용자는 모든 값을 고칠 수 있고, 모달 안의 카드 선택 줄로 다른 예시 숙소를 불러올 수 있다. "불러온 값 해제"로 되돌림. 검색하면 선택한 숙소가 결과 맨 위에 온다 |
| 예산 필드 | "1박 최대 예산(원, 선택)" 신규. 결과에서 이 금액 이하만 보여 준다 |
| 챗봇 진입 | 화면 우하단 "숙소 도우미에게 묻기" 버튼, 그리고 "궁금한 건 물어보세요" 제목 옆 채팅 아이콘. 둘 다 같은 채팅창을 연다 |

### 챗봇 표시 방식 결정: 페이지 이동이 아니라 도킹된 채팅 패널 + 인라인 정보 카드 (제안)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 질문마다 웹페이지 이동 | 정보를 크게 보여 줌 | 대화 맥락과 화면 상태(검색 조건)를 잃음, 왕복이 잦아 이탈 |
| B. 답변마다 모달 | 화면 이동 없음 | 대화를 가리고 모달이 겹침, 모바일에서 답답함 |
| C. 도킹 패널 + 답변 안 정보 카드 + 출처 칩 펼침 (추천) | 대화 흐름 유지, 페이지를 옮겨도 패널이 유지됨, 모바일은 하단 시트 | 패널 폭이 좁아 긴 정보는 카드로 요약 필요 |

- 추천 C. 근거: RAG 답변은 짧고 출처가 붙는 형태라 대화창 안에서 끝나는 경우가 대부분이고, 대화 중에 검색 조건·결과 화면이 유지되어야 한다.
- 페이지 이동은 사용자가 카드의 "이 숙소 보러 가기"를 눌렀을 때만 한다(긴 정보나 예약).
- 답변마다 "AI가 생성한 답변" 표시, 출처 칩(하우스 룰·숙소 정보)을 누르면 발췌문을 그 자리에서 펼친다.
- 실시간 가격·예약 가능 여부는 단정하지 않고 예약 화면으로 안내한다(01장 6.1절). 근거가 없으면 "찾지 못했어요" + 호스트 문의(가입 필요).
- 디자인 속 답변 내용은 모두 예시이며 실제 RAG(02장 5절) 응답 계약은 04장 6.2절을 따른다.
