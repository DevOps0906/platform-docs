## 2. 설득 흐름: 제품 랜딩의 공통 뼈대

기존 제품 랜딩은 "결과물이 주인공인 히어로 → 결과물 → 만드는 순서 → 요금"으로 이미 짜여 있다. 이 흐름에 **문제·원인·필요성 검증** 세 칸을 끼워 넣는다. 섹션 수는 7~8개를 넘기지 않는다(`DESIGN_PRINCIPLES.md` "섹션 수를 줄이고").

| 순서 | 칸 | 묻는 질문 | 채우는 것 | 시각 규칙 |
|---|---|---|---|---|
| 1 | 히어로 | 이게 뭔가? | 결과물(실제 렌더)과 한 줄 정의, CTA 하나 | 기존 제품 03장 4절 그대로 |
| 2 | 막히는 지점 | 나도 이 문제를 겪나? | 페르소나가 실제로 막히는 장면 2~3개(01장 1절 "좌절" 열에서 가져온다) | 장면 묘사 문장 + 실제 화면 조각. 아이콘 카드 그리드 금지 |
| 3 | 원인 하나 | 왜 계속 막히나? | 문제를 만드는 원인 한 가지를 한 문장으로 | 기존 방식 / 제품 방식 비교 카드 1쌍(4장) |
| 4 | 방식 | 어떻게 푸나? | 제품의 실제 순서(단계 레일)와 "사용자가 하는 일 / 제품이 하는 일" 이중 타임라인 | 실제 순서일 때만 번호 사용(기본값 10번) |
| 5 | 왜 이 플랫폼인가 | 다른 방법이 아니라 왜 이것인가? | 대안 판정표, 증거 링크, 맞지 않는 경우(3장) | 표 1개. 카드 그리드 금지 |
| 6 | 비용·시간 비교 | 나한테 얼마나 이득인가? | 가정 조건이 보이는 계산기(6장). 수치를 미리 넣지 않는다 | 표와 입력란. 큰 숫자 타일 금지(기본값 6번) |
| 7 | 행동 | 지금 뭘 하면 되나? | 무료 시작 또는 샘플 받기 하나 + 요금·FAQ | CTA 하나 |

규칙:

| 규칙 | 내용 |
|---|---|
| 순서 고정 아님 | 2~6칸 순서는 제품 03장에서 바꿀 수 있다. 단 5칸(왜 이 플랫폼인가)은 빼지 않는다 |
| 감정 → 논리 → 돈 | 2칸은 페르소나 언어로, 3~5칸은 사실과 증거로, 6칸은 사용자가 넣은 숫자로 말한다 |
| 한 화면 한 주장 | 섹션마다 주장 하나. 주장은 주장 장부(3.4절)에 등록된 것만 쓴다 |
| 모션 | 기존 제품 규칙대로 연출 순간은 히어로 하나. 이 문서의 칸들은 정지 상태로 읽혀야 한다 |
| 언어 | 칸 이름(막히는 지점, 원인 등)은 내부 구조 이름이다. 화면에 영어·대문자 라벨로 붙이지 않는다(`DESIGN_PRINCIPLES.md:204`) |

## 3. "왜 이 플랫폼이어야 하는가" 검증

이 칸의 목적은 방문자를 설득하는 것만이 아니다. **우리 스스로 "이 제품이 꼭 있어야 하는가"를 확인하는 장치**다. 판정표를 정직하게 채웠을 때 우리 열이 대안보다 낫지 않으면, 랜딩 문구가 아니라 제품 범위를 다시 본다.

### 3.1 대안 지도

고객이 지금 이 일을 하는 방법을 범주로 적는다. 5개 범주를 기본으로 하고 제품에 없는 범주는 뺀다.

| 범주 | 뜻 | 예 |
|---|---|---|
| 그대로 둔다 | 지금 하던 대로 손으로 한다(현상 유지) | 워드프로세서, 엑셀, CAD에서 직접 |
| 범용 AI 채팅 | 범용 AI 챗봇에 묻고 결과를 복사해 붙인다 | 대화형 AI 서비스 |
| 사람에게 맡긴다 | 외주·대행·협력사에 맡긴다 | 프리랜서 마켓의 대행 상품 |
| 전문 도구 | 같은 일을 하는 국내외 전용 도구 | 제품별 `Price_Plans/<제품>/PRICE_PLAN.md` 4장 경쟁 표 |
| 안 한다 | 그 일을 포기하거나 미룬다 | 출판 포기, 제안 생략 |

랜딩에는 **범주 이름만** 쓰고 특정 회사·서비스 이름과 로고를 쓰지 않는다(3.5절). 내부 분석(가격 플랜 4장)에는 출처·확인일과 함께 실명을 쓴다.

### 3.2 판정 기준과 판정표

| 규칙 | 내용 |
|---|---|
| 기준 수 | 4~6개. 고객이 실제로 고르는 기준이어야 한다. 출처는 01장 1절 페르소나의 "좌절" 열과 고객 인터뷰(3.6절 V0) |
| 판정 값 | ○(된다) △(일부·조건부) ✕(안 된다). 색만으로 구분하지 않고 기호와 한 줄 근거를 같은 칸에 쓴다 |
| 우리 열의 정직성 | 우리 열이 전부 ○이면 다시 본다. 실제로 약한 기준(가격, 학습 비용, 지원 범위 등) 하나 이상을 △나 ✕로 적는다. 전부 ○인 판정표는 믿지 않는다 |
| 증거 연결 | 우리 열의 ○마다 증거(3.3절) 하나를 링크한다. 증거가 없는 ○는 △로 내리거나 행을 지운다 |
| 대안 열의 근거 | 대안의 ✕·△도 근거 한 줄을 쓴다. "직접 해 보면 알 수 있는 사실"만 쓴다(예: "쪽번호·러닝 헤더를 손으로 넣어야 합니다"). 타사 기능에 대한 단정은 쓰지 않는다 |
| 맞지 않는 경우 | 표 아래에 "이런 경우엔 다른 방법이 낫습니다" 2~3행을 둔다. 신뢰를 만들고 환불·이탈을 줄인다 |

판정표 형식(제품 03장에 이 형식으로 둔다):

| 기준 | 그대로 둔다 | 범용 AI 채팅 | 사람에게 맡긴다 | 이 제품 | 우리 열 증거 |
|---|---|---|---|---|---|
| (고객이 고르는 기준) | ○△✕ + 근거 한 줄 | ○△✕ + 근거 | ○△✕ + 근거 | ○△✕ + 근거 | 증거 ID(3.3절) |

### 3.3 증거 등급

증거는 방문자가 **직접 확인할 수 있는 정도**로 등급을 매긴다. 등급이 높을수록 랜딩 위쪽에 둔다.

| 등급 | 증거 | 예 | 조건 |
|---|---|---|---|
| E1 | 가입 없이 직접 해 보기 | 예시 데이터로 도는 체험, 판형 바꿔 보기 | 실제 엔진 출력이어야 한다(가짜 애니메이션 금지) |
| E2 | 실제 결과 파일 내려받기 | 샘플 PDF·ePub·DXF·문서 묶음 | CI가 엔진 출력에서 만든 파일만. 손으로 다듬은 파일 금지 |
| E3 | 실제 화면 기록 | 편집 없는 화면 녹화(배속 표시) | 연출 목업·기기 프레임 금지 |
| E4 | 측정 기록 | "5명, 같은 원고, 중앙값 N분"(조건·인원·기간 표기) | 3.6절 V1 이후. 측정 조건 없이 숫자만 쓰지 않는다 |
| E5 | 실제 고객 사례 | 실명·동의를 받은 사례 | 유료 고객 이후. 가상 후기 금지 |

출처 없는 업계 통계, 2차 인용 통계, 원문을 확인하지 않은 논문 인용은 증거로 쓰지 않는다.

### 3.4 주장 장부

랜딩·인사이트·광고에 나가는 주장은 모두 한 장부에 등록하고, 상태가 "검증"인 것만 게시한다. 제품 03장에 초안을 두고, 개발 폴더에서는 랜딩 작업이 `docs/<제품>/experiments/claims-ledger.md`로 관리한다.

| 열 | 내용 |
|---|---|
| ID | `<제품 약어>-C-01` |
| 주장 | 화면에 나갈 문장 그대로 |
| 유형 | 기능 사실 / 비교 / 측정치 / 가정 추정 |
| 증거 | 증거 등급과 링크(3.3절) |
| 검증 방법 | 누가 무엇으로 확인하나 |
| 상태 | 초안 / 검증 / 보류 / 폐기 |
| 확인일 | 마지막 확인 날짜 |

| 상태 규칙 | 내용 |
|---|---|
| 초안 | 게시 금지 |
| 검증 | 게시 가능. 측정치는 측정 조건 문구와 함께만 |
| 보류 | 기능 출시 전이거나 법무 확인 대기. 게시 금지 |
| 폐기 | 근거가 무너졌거나 측정 결과가 주장과 다르다. 다시 쓰지 않는다 |

| 항목 | 규칙 |
|---|---|
| 실명 비교 | 특정 회사·서비스 이름을 넣은 비교는 객관적·검증 가능한 사실과 근거 자료 보관이 필요하다. 「표시·광고의 공정화에 관한 법률」과 공정거래위원회 비교 표시·광고 심사지침의 적용 조건은 미확인이며 법무 확인 전에는 랜딩에 실명 비교를 쓰지 않는다 |
| 상표 | 타사 로고를 쓰지 않는다. 호환을 말할 때는 "○○ 파일 호환"처럼 사실만(arch-studio 01장 6.1절 방식) |
| 가격 비교 | 출처, 확인일, 환율, 세금 포함 여부를 함께 적는다. 확인일이 90일 지난 가격은 다시 확인하기 전까지 내린다(제안) |
| 측정치 | 측정 조건(인원, 과업, 기간, 도구 버전)을 숫자 바로 옆에 둔다 |

### 3.6 필요성 검증 단계 (린)

개발보다 검증을 먼저 한다. 각 단계는 앞 단계의 결과로 다음 단계 진입을 정한다. 기준값은 모두 제안이다.

| 단계 | 시점 | 하는 일 | 비용 | 통과 기준(제안) | 실패하면 |
|---|---|---|---|---|---|
| V0 인터뷰 | 개발 전 | 페르소나 5명에게 "지금 이 일을 어떻게 하나요? 제일 오래 걸리거나 짜증 나는 곳은?"을 묻는다. 제품 설명은 마지막에만. 판정 기준을 고객 언어로 확정 | 0원(시간만) | 5명 중 3명 이상이 같은 불편을 먼저 꺼낸다 | 판정 기준을 고치거나 페르소나를 바꾼다. 같은 불편이 안 나오면 제품 범위 재검토 |
| V0 랜딩 | 개발 전(대기자 랜딩) | "왜 이 플랫폼인가" 칸이 있는 판과 없는 판을 기간을 나눠 번갈아 건다(각 2주, 방문 1,000 이상) | 0원 | 있는 판의 대기자 등록률이 낮지 않다 | 판정표 문구가 혼란을 준다는 뜻. 표를 줄이거나 증거를 위로 올린다 |
| V1 과업 측정 | MVP 직후 | 5명이 같은 과업을 자기 방법과 제품으로 각각 한다. 시간, 막힌 지점, 결과물 품질(체크리스트)을 기록 | 소액 사례비(제안) | 5명 중 4명 이상이 제품 쪽 시간이 짧고 결과물 체크리스트 통과 | 주장 장부의 시간 관련 주장을 폐기하고 원인을 06장 작업으로 만든다 |
| V2 실측 | 공개 베타 | 제품 이벤트로 "가입 → 첫 결과물" 시간과 완료율을 잰다 | 0원 | 01장 KPI 목표 | 랜딩 문구를 실측 중앙값으로 교체하거나 문구를 내린다 |
| V3 사례 | 유료 고객 이후 | 동의를 받은 실제 사례 2건으로 판정표 아래 사례 칸을 채운다 | 0원 | 사례 2건 | 사례 칸 없이 운영 |

V0 두 실험은 개발 없이 할 수 있는 가장 싼 검증이다. 결과는 개발 폴더 task `log.md`에 `[DECISION]`으로 남긴다.

## 4. 컴포넌트 (구조 패턴)

원자료의 컴포넌트를 이 저장소 원칙에 맞춰 다시 정의한다. 토큰은 제품 03장 4절 값만 쓰고, 제품 디자인 시스템(`web/src/components/`)에서 만든다. 마케팅 전용 컴포넌트는 앱 화면에 쓰지 않는다.

| 컴포넌트 | 쓰는 칸 | 구조 | 지킬 것 |
|---|---|---|---|
| AlternativesTable(대안 판정표) | 5 | 표: 행 = 기준, 열 = 대안 범주 + 우리, 칸 = 기호 + 한 줄 근거, 마지막 열 = 증거 링크. 모바일은 "기준 하나 = 블록 하나"로 접힌다 | 기호 + 텍스트(색만 금지), 가로 스크롤은 표 안에서만, `<table>`과 `scope` 속성 |
| ContrastPair(기존 방식 / 제품 방식) | 3 | 2열, 같은 속성을 같은 줄에. 모바일은 속성마다 위아래 | 페이지에 1쌍만. 빨강·초록 대비 대신 제품 토큰의 중립색 + 기호 |
| StepRail(단계 레일) | 4 | 실제 처리 순서만. 마지막 칸이 결과물 | 순서가 아닌 내용에 번호 금지(기본값 10번) |
| DualTimeline(이중 타임라인) | 4, 앱 작업 상세 | 단계마다 두 줄: "사용자가 하는 일" / "제품이 하는 일". 승인 지점은 사용자 줄에 표시 | AI가 한 일과 사람이 결정한 일을 섞지 않는다 |
| ProofLink(증거 링크) | 5 | 증거 등급(E1~E5)에 맞는 동작 문구: "샘플 PDF 받기", "가입 없이 해 보기" | 링크 끝 화살표 금지(기본값 5번). 버튼 문구는 일어나는 일을 말한다 |
| AssumptionTable(가정 조건 표) | 6 | 계산에 쓴 가정을 행으로: 값, 누가 넣었나(사용자 / 출처), 출처·확인일 | 출처 없는 기본값 금지 |
| Callout(결론 한 줄) | 3~6 중 한 곳 | 왼쪽 띠 + 결론 한 문장 + 설명 한 줄 | 페이지에 1개 |
| SourceNote(출처 한 줄) | 모든 칸 | 표·주장 아래 작은 글씨 "출처: …, 확인일 …" | 출처가 없으면 주장을 지운다 |
| SampleTag("예시"·"샘플" 표시) | 1, 5, 6 | 예시 데이터·샘플 결과물 옆 작은 표시 | 실제 고객 결과물이 생겨도 동의 전에는 유지 |
| ContactButton(문의) | 전역(선택) | 고정 위치 버튼 하나, 누르면 문의 경로(메일·채널) | 자동으로 뜨는 말풍선·팝업 금지. 문구는 "문의하기"처럼 동작만 |

쓰지 않는 원자료 컴포넌트: GlassCard(같은 둥근 카드 반복, 기본값 4번), KpiTile·DonutStat·카운트업(마케팅 큰 숫자, 기본값 6번), 영어 아이브로 SectionHeader(기본값 5·8번), 시머 텍스트, PainCard 호버 블러(기본값 11번), JobPosting 스탬프(1장 11번).

## 5. 논증형 아티클(인사이트 시리즈)

검색 유입과 재방문을 위한 글 묶음이다. 랜딩 5칸의 판정 기준 하나를 글 한 편으로 깊게 설명한다.

| 항목 | 규칙 |
|---|---|
| 편수 | 3편을 한 시리즈로. 마지막 편은 6칸 계산기나 가입으로 잇는다 |
| 단계 | 주장(한 문장) → 대비(헷갈리는 두 개념을 같은 속성으로 비교) → 증상(독자가 겪는 장면 3개) → 논거(원리 설명) → 우리 방식(실제 순서) → 증거(3.3절 등급) → 다음 편 |
| 화면 라벨 | 단계 이름을 화면에 쓰지 않는다. 각 단계는 한국어 소제목 문장으로 시작한다 |
| 인용 | 외부 인용은 원문을 직접 확인한 것만, 출처·확인일과 함께. 확인하지 못한 통계는 쓰지 않는다 |
| 주제 | 제품의 고유 원리에서 뽑는다. A-RMS·키트의 시리즈 제목과 주장 문장은 쓰지 않는다(1장 9번) |
| 구현 | 정적 MDX(`web/content/insight/*.mdx`), 경로 `/insight/[slug]`, `generateStaticParams`. 메타 설명·OG 이미지·사이트맵 포함 |
| 시각 | 제품 marketing 레이어 토큰. 본문 폭 최대 72자, 그림은 실제 화면·실제 결과물 |
| 우선순위 | 공개 베타 조건이 아니다(P1~P2). V0 인터뷰 결과로 주제를 확정한 뒤 쓴다 |

## 6. 비용·시간 비교 계산기

원자료의 ROI 대시보드(큰 숫자 타일 5개, 누적 막대) 대신 **사용자가 자기 숫자를 넣는 계산기**를 쓴다. 우리가 수치를 정하지 않으므로 허위 수치 위험이 없다.

| 규칙 | 내용 |
|---|---|
| 입력 | 사용자가 넣는다: 작업 건수, 건당 시간, 시간 단가, 외주 견적 등. 기본값을 두려면 출처·확인일이 있는 값만(가격 플랜 4장) |
| 계산 | 클라이언트 순수 함수. 서버 저장 없음. 공식을 화면에 그대로 보여 준다 |
| 결과 | 표로 보여 준다(대안별 비용·시간). 큰 숫자 타일·카운트업 금지 |
| 고지 | 결과 바로 아래 "입력한 가정으로 계산한 추정치이며 실제 결과와 다를 수 있습니다" |
| 리드 수집 | 결과는 이메일 없이 먼저 보여 준다(결과를 이메일 뒤에 숨기지 않는다). 그 아래 기존 대기자·가입 폼을 선택으로 둔다. 결과 PDF는 브라우저 인쇄·저장으로 |
| 측정 | 계산 실행·폼 제출은 분석 이벤트로만 센다. 입력값은 수집하지 않는다 |
