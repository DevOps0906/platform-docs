# DESIGN_SYSTEM — 12개 제품 공통 디자인 시스템 구축 규칙

작성일 2026-10-13. 모든 제품의 UI 구현 에이전트와 사람 담당자는 컴포넌트·토큰을 만들거나 고치기 전에 이 문서를 따른다. 화면 디자인 절차는 `DESIGN_PRINCIPLES.md`, 메인 히어로는 `HERO_3D.md`, 제품별 레퍼런스와 브랜드 토큰은 `REFERENCES.md`, 스킬은 `SKILLS.md`, 앱 화면의 구조(패턴 A~O)는 `DASHBOARD_PATTERNS.md`에 있다. 이 문서는 "무엇을 정답으로 두고, AI에게 어디까지 맡기는가"를 정한다.

세 레퍼런스는 **라이브러리를 설치해 쓰는 대상이 아니라 패턴·밀도·토큰 체계를 배우는 대상**이다. 이 플랫폼의 구현 스택은 Tailwind CSS v4 + shadcn/ui로 고정이고, 세 시스템은 각자 다른 스타일 방식(Primer는 자체 CSS, Astryx는 StyleX 등)을 쓰므로 그대로 섞지 않는다.

## 2. 원칙 (실무 사례에서 얻은 다섯 가지)

| 원칙 | 내용 | 사례 근거 |
|---|---|---|
| AI에게 "알아서"는 없다 | "분석해서 없는 걸 만들어줘"는 성립하지 않는다. 컴포넌트마다 크기·radius·border·글자 크기·line-height·토큰을 하나하나 지정한다 | 실패 1: 토큰 변수를 두고 hex를 박고, 기존 버튼 복제도 height·색이 틀림 |
| 토대가 먼저다 | 빠진 컴포넌트와 배리언트가 많으면 좋은 도구(Storybook 하네스 등)를 얹어도 채워지지 않는다. 기본 컴포넌트와 배리언트 목록을 먼저 채운다 | 실패 2 |
| 경계를 준다 | 프라이머리 컬러 하나만 주고 통째로 맡기면 "평범한 양산형"이 나온다. 레퍼런스, 토큰, 금지 목록, 배리언트 표로 AI의 선택 공간을 좁힌다 | 실패 3: 일주일 5천 달러, 결과는 어디서 본 듯한 시스템 |
| 전부 명시한다 | 명시하지 않은 것은 AI가 "가장 흔한 것"으로 추론한다. 특히 버전: **Tailwind는 반드시 v4**라고 적는다 | 실패 4: "Tailwind"라고만 해서 v3로 만들어졌고, 라이트/다크 전환 중에야 발견 |
| 맡기는 크기 = 검증할 수 있는 크기 | 사람이 검증할 수 없는 크기의 작업을 AI에게 넘기지 않는다. 컴포넌트 단위로 맡기고 바로 확인한다 | 사례의 결론 |

## 3. 정답 소스(Single Source of Truth)

| 항목 | 정답 | 아닌 것 |
|---|---|---|
| 디자인 토큰 | 제품 저장소의 Tailwind v4 CSS: `apps/web/src/styles/tokens.css`의 `@theme` 블록(색, 서체, 간격, radius, 그림자, 모션)과 라이트/다크 변수 | 피그마 변수, 문서 속 hex 표, `tailwind.config.js` |
| 컴포넌트 | 제품 저장소의 코드 컴포넌트(`apps/web/src/components/ui/`, shadcn/ui 기반을 토큰으로 재스타일) | 피그마 컴포넌트, 다른 라이브러리 그대로 설치 |
| 문서 | `docs/file/03-설계/디자인/` 아래 `DESIGN.md`(토큰 표)와 `COMPONENTS.md`(컴포넌트·배리언트 표). 코드에서 뽑아 갱신하고, 코드와 다르면 코드가 이긴다 | 코드와 따로 손으로 관리하는 문서 |
| 시각 확인 | 컴포넌트 미리보기 페이지(`/dev/components` 또는 Storybook, 제품 선택)의 라이트/다크 스크린샷 | 피그마 시안 |

- 정답이 두 곳이면 AI는 편한 쪽으로 샌다. 피그마를 쓰더라도 초안 단계에서만 쓰고, 코드로 옮긴 뒤에는 정답으로 삼지 않는다.
- 문서에는 피그마 노드 ID, 외부 파일 링크, 생성용 지름길을 남기지 않는다. 문서만으로 같은 결과를 재현할 수 있어야 한다(7장).
- 개발용 위키(`docs/wiki/`, `LLM_WIKI.md`)는 이 정답을 요약할 뿐 대체하지 않는다.

## 4. 구축 워크플로 (4단계)

| 단계 | 할 일 | 산출물 | 담당 |
|---|---|---|---|
| 1. 레퍼런스를 명확히 정한다 | 제품 성격에 맞는 주 레퍼런스를 5장 표에서 고르고, 가져올 패턴과 가져오지 않을 것을 적는다 | `DESIGN.md` 1절 "레퍼런스와 방향" | 고문(Fable) 검토 |
| 2. 가진 것 위에서 시작한다 | 기존 브랜드 토큰(`REFERENCES.md`의 제품 절, 03장 토큰 플랜) + 프라이머리 컬러 + Tailwind v4 `@theme`으로 토큰을 먼저 확정하고, 그 위에서 기본 컴포넌트를 만든다. 제품 고유 컴포넌트는 기본 세트가 끝난 뒤 | `tokens.css`, 기본 컴포넌트, `COMPONENTS.md` 배리언트 표 | 부(Sonnet) 구현, 주(Opus) 설계 |
| 3. 비주얼은 사람이 빚는다 | 컴포넌트마다 라이트/다크, 상태(기본·호버·포커스·비활성·오류·로딩), 크기 배리언트를 스크린샷으로 보고 사람이 수치를 고친다. 이 단계는 줄이지 않는다 | 미리보기 페이지 스크린샷, 수정 기록 | 사람 + 부(Sonnet) |
| 4. 정답을 한 곳으로 옮긴다 | 코드(Tailwind v4 CSS + 컴포넌트)를 정답으로 확정하고, 문서를 코드 기준으로 다시 맞춘다. 초안용 피그마 노드는 정답에서 지운다 | 확정된 `DESIGN.md`, `COMPONENTS.md` | 주(Opus) |

- 1~4단계는 제품 06장 작업 계획의 W0~W1(기반)에 둔다. 화면 작업은 4단계가 끝난 뒤 시작한다.
- 이후 수정은 브라우저에서 요소를 직접 확인하며 바꾸고, 바꿀 때마다 문서를 함께 맞춘다.

## 6. 기술 규칙

| 항목 | 규칙 |
|---|---|
| Tailwind | **반드시 v4**. CSS 우선 설정(`@import "tailwindcss";`, `@theme`, `@custom-variant dark`)을 쓴다. `tailwind.config.js`와 v3 문법(`@tailwind base` 등)은 쓰지 않는다. 패키지 버전은 4.x로 고정하고 `latest`를 쓰지 않는다 |
| shadcn/ui | Tailwind v4를 지원하는 버전으로 설치하고, 컴포넌트는 저장소에 복사된 코드를 토큰으로 재스타일한다 |
| 토큰 이름 | 의미 기반(`--color-surface`, `--color-text-muted`, `--color-accent`, `--radius-control`)으로 짓고 hex를 컴포넌트에 직접 쓰지 않는다. 린트로 막는다(제안: 임의 값 `bg-[#...]` 금지 규칙) |
| 다크 모드 | 처음부터 라이트/다크 두 벌의 토큰을 둔다. 전환은 `data-theme` 또는 `.dark` 한 가지로 통일 |
| 밀도 | 대시보드는 컴팩트/기본 두 밀도를 토큰(간격, 행 높이)으로 지원한다(Primer식) |
| 접근성 | 대비 WCAG AA, 포커스 링 토큰, 키보드 조작, 상태는 색만으로 표시하지 않는다(Atlassian식 배지 + 아이콘·텍스트) |
| 버전 명시 | 문서·작업 지시에 라이브러리 버전을 항상 적는다(Next.js, React, Tailwind v4, shadcn, three.js 등) |

## 7. 금지 사항

- "알아서 디자인 시스템을 만들어줘", "우리 것을 분석해서 없는 걸 채워줘" 같은 범위 없는 지시.
- 프라이머리 컬러만 주고 전체 시스템을 한 번에 생성시키는 일(비용이 크고 결과가 평범해진다).
- 문서에 피그마 노드 ID·외부 파일 링크를 남겨 AI가 문서 대신 원본을 복사하게 만드는 일.
- 정답 소스를 두 곳(피그마와 코드, 또는 문서와 코드)에 두는 일.
- 버전을 적지 않은 지시. 특히 "Tailwind로"(반드시 "Tailwind v4로").
- 검증할 수 없는 크기의 작업을 한 번에 맡기는 일. 컴포넌트·배리언트 단위로 나눠 맡기고 바로 확인한다.

## 9. 제품 문서 반영 규칙
- 각 제품 `03_SCREENS_UX.md`에 "디자인 시스템" 항목을 둔다: 주 레퍼런스(5장), 토큰 파일 위치, 기본 컴포넌트·배리언트 목록, 정답 소스 위치.
- 각 제품 `06_AGENT_PLAN.md`의 W0~W1에 4장 1~4단계 작업을 둔다. 3단계(사람 비주얼 검토)는 사람이 수행하는 작업으로 명시한다.
- 개발 폴더(`<제품>-root/docs/file/03-설계/디자인/`)에는 이 문서와 함께 `DESIGN.md`, `COMPONENTS.md`의 초기 템플릿을 둔다.
- 각 제품 `03_SCREENS_UX.md` 화면 목록 표에 `패턴` 열을 두고 `DASHBOARD_PATTERNS.md`의 코드(A~O, 맞지 않으면 `고유`)를 적는다. 열이 아직 없는 제품은 다음에 그 화면 표를 고칠 때 함께 채운다.
