## 1. 프로젝트 개요

- 한 줄 설명: 여러 증권사 계좌를 한 화면에 모아 실시간 시세와 손익을 보여주고, Claude/GPT/Gemini가 투자 성향별 종목 추천(매수가/목표가/손절가)을 스트리밍으로 제시하며, AI별 추천 성과를 리더보드로 공개하는 주식 대시보드 "InvestGEN" (`PRD.md:4-5`).
- 기획 의도: 초보자의 진입 장벽 완화, 단일 AI 편향을 멀티 AI 비교로 보완, 실시간 정보 비대칭 해소 (`PRD.md:13-15`).
- 대상 사용자: FOMO를 겪는 초보 개인 투자자, 여러 증권사에 자산이 흩어진 투자자, AI 제안을 즉시 포트폴리오에 반영하려는 사용자 (`PRD.md:6-8`).
- 폴더명은 "Stock_Trader"지만 문서 어디에도 주문(매수/매도 실행) 기능은 없다. 현재 기획은 조회와 추천 서비스이며, "AI 제안을 포트폴리오에 즉각 반영"(`PRD.md:8`)이라는 문구만 자동매매로 확장될 여지를 남긴다.

심각도 높음 항목 상세:
- #1 (키/계좌 보관): 증권사 app secret과 접근 토큰이 유출되면 계좌 조회와, 권한에 따라 주문까지 가능해진다. 키는 서버에만 두고 브라우저에는 절대 내려보내지 않는다. 다중 사용자라면 사용자별 키를 AES-256-GCM으로 암호화해 저장하되 키 암호화 키(KEK)는 환경변수나 Supabase Vault에 두고, 해당 테이블은 RLS로 모든 클라이언트 접근을 막고 service role 경로에서만 읽는다. 계좌번호는 화면과 로그에서 마스킹한다. 스크래핑(ID/비밀번호 저장)은 요구사항에서 제외한다.
- #2 (주문 안전장치): 주문 기능을 넣는 순간 버그 한 번이 금전 손실로 이어진다. 4장의 "주문 안전장치" 요구를 PRD에 별도 절로 추가하고, 이 장치가 모의투자 환경에서 검증되기 전에는 실전 주문 경로를 코드에 두지 않는 것을 원칙으로 한다.
- #3, #4 (법적 리스크): 본인만 쓰는 개인 도구라면 대부분 해소된다. 공개 서비스로 운영하려면 (a) 유사투자자문업 신고 또는 투자자문업 등록, (b) 마이데이터 허가 또는 사용자가 직접 연결하는 구조, (c) 시세 재배포 약관 확인이 필요하다. 이 판단은 개발 범위를 좌우하므로 착수 전에 "개인용/공개용"을 결정해야 한다. 본 리뷰는 법률 자문이 아니며, 공개 서비스로 가려면 전문가 검토를 받아야 한다.
- #5, #6 (연동/실시간): 증권사 API 검증 없이 UI부터 만들면 데이터 모델이 증권사 응답 형태와 맞지 않아 다시 짜야 한다. 상주 워커가 증권사 WebSocket을 구독하고, Supabase Realtime 또는 워커의 SSE 엔드포인트로 브라우저에 중계하는 구조를 먼저 확정해야 한다.

## 4. 효율적 구현 전략

### 4.1 권장 아키텍처

- 웹: Next.js 16 App Router + Tailwind v4 + shadcn/ui + Recharts(차트 라이브러리는 하나로 고정). Node 런타임.
- 인증/DB: Supabase Auth + Postgres + RLS. 테이블 초안은 `broker_connections`(암호화 키, 모의/실전 구분), `holdings_snapshots`, `trades`(매매 일지), `ai_recommendations`(모델, 전략, 입력 스냅샷 해시, 출력 JSON), `recommendation_results`(평가 시점별 수익률), `audit_logs`.
- 증권사 연동: `BrokerAdapter` 인터페이스(`getBalance`, `getHoldings`, `getExecutions`, `subscribeQuotes`)를 정의하고 `MockBroker`, 첫 번째 실제 증권사 어댑터 순으로 구현한다. UI는 어댑터만 바라보므로 `claude.md`의 목업 단계와 실데이터 단계가 같은 코드 경로를 쓴다.
- 실시간: 상주 워커(Node, Railway 등) 1개가 증권사 WebSocket을 구독해 Supabase Realtime 채널(또는 워커 자체 SSE)로 중계한다. Vercel 함수에서 장시간 SSE를 유지하지 않는다. 브라우저 상태는 zustand의 종목별 셀렉터로 원자적 갱신을 구현한다.
- AI: OpenRouter 단일 키로 모델 ID만 바꾸는 구조(모델 목록은 설정 파일). 서버 라우트가 포트폴리오와 시세 스냅샷을 프롬프트에 주입하고, 출력은 zod 스키마로 검증하며(종목코드 실존, 가격 범위), 응답은 `fetch(POST)` + `ReadableStream`으로 스트리밍한다.
- 리더보드: 일 1회 배치(장 마감 후)로 `recommendation_results`를 계산한다. 계산 규칙은 문서로 고정하고 초기에는 로그인 사용자에게만 보인다. GEO 공개는 법률 검토 후로 미룬다.

### 4.2 증권사 키와 주문 안전장치 (요구사항에 추가할 항목)

| 항목 | 요구 내용 |
|------|----------|
| 키 보관 | 서버 전용(`server-only` 모듈). 단일 사용자는 환경변수, 다중 사용자는 AES-256-GCM 암호화 컬럼 + KEK 분리. 키 미설정 시 기동 실패(기본값 폴백 금지). 접근 토큰은 서버 캐시, 만료 전 갱신 |
| 계좌정보 | 계좌번호 마스킹 표시, 로그/에러 메시지에서 키, 토큰, 계좌번호 제거 |
| 모의투자 우선 | 환경 플래그 기본값은 모의(`BROKER_ENV=paper`). 실전 전환은 서버 설정 + 사용자 재인증 + 화면 상단 고정 배너. 연결 단위로 모의/실전을 저장하고 섞지 않는다 |
| 주문 한도 | 1회 주문 금액, 일일 누적 금액, 종목별 최대 비중, 일일 주문 건수 상한을 서버에서 강제. 현재가 대비 지정가 괴리(예: 5% 초과) 거부 |
| 중복 주문 방지 | 클라이언트가 만든 주문 ID(idempotency key)를 DB unique 제약으로 저장하고, 주문 상태 머신(요청 -> 접수 -> 체결/거부/취소)으로 재시도 시 재전송을 막는다. 버튼 연타 방지는 보조 수단일 뿐이다 |
| 장애 시 정지 | 전역 킬 스위치(DB 플래그). 시세 지연(마지막 틱 N초 초과), 증권사 오류 연속 N회, 잔고 불일치 감지 시 자동으로 신규 주문을 차단하고 알림을 보낸다 |
| AI와 주문 분리 | AI 추천은 주문을 직접 만들지 않는다. 사용자가 확인 화면에서 수량과 가격을 확인하고 승인해야 주문이 생성된다 |
| 감사 로그 | 모든 주문 요청, 한도 판정 결과, 증권사 응답을 변경 불가 로그로 남긴다 |

### 4.4 MVP 범위 축소안

- 포함: 본인 전용(단일 사용자) 조회 대시보드, 증권사 1곳(모의투자 계좌), 잔고/보유종목/체결내역 조회, 장중 시세 반영(워커 중계), 종목 상세 모달(재무지표는 DART 또는 증권사 제공분), AI 1개 모델로 "포트폴리오 진단" 리포트(종목별 목표가/손절가 대신 리스크 요인과 분산 상태 설명), 추천 이력 저장.
- 제외(2단계 이후): 두 번째 증권사, AI 3사 비교 탭, 공개 리더보드, GEO/JSON-LD, 주문 기능, 스크래핑(영구 제외).

### 4.5 단계별 로드맵

1. 0단계 (1주): 개인용/공개용 결정과 법률 검토 범위 확정, 증권사 API 기술 검증(인증, 잔고, 시세 WebSocket, 모의투자 서버), PRD에 데이터 모델과 4.2 안전장치 절 추가.
2. 1단계 (2~3주): 골격(sellingstudio 이식) + `BrokerAdapter`/`MockBroker` + 목업 대시보드 UI(`claude.md` 지침 그대로) + 키 암호화 저장.
3. 2단계 (2~3주): 실제 증권사 어댑터(조회 전용), 시세 워커와 Realtime 중계, 매매 일지 동기화, 상세 모달 재무지표.
4. 3단계 (2주): AI 진단(스트리밍, 스키마 검증, 비용 상한), 추천 이력과 성과 배치, 내부용 리더보드.
5. 4단계 (선택, 법률 검토 후): 모의투자 주문(4.2 안전장치 전부 포함) -> 실전 전환, 멀티 AI 비교, 공개 리더보드와 GEO.

## 6. 종합 평가

- 실현 가능성: 본인 전용 조회 대시보드 + AI 진단으로 범위를 줄이면 7~9주 안에 실현 가능하다. PRD 그대로의 공개 서비스(타인 계좌 통합, 종목별 매수/목표/손절가 추천, 공개 리더보드)는 기술보다 법적 요건(투자자문, 마이데이터, 시세 재배포) 때문에 현재 형태로는 출시하기 어렵다.
- 강점: (1) 화면 구성과 디자인 지침이 구체적이라 UI 프로토타입은 빠르게 만들 수 있다. (2) 멀티 AI 비교와 성과 추적이라는 차별화 포인트가 분명하다. (3) 워크스페이스에 인증, UI, 차트, 암호화, LLM 클라이언트 모듈이 이미 있어 골격 비용이 낮다.
- 약점: (1) 증권사 키 보관과 주문 안전장치가 전혀 정의되지 않았다. (2) 투자자문업, 마이데이터 관련 법적 검토가 없다. (3) 백엔드, 데이터 모델, 실시간 중계 구조가 없어 Vercel 단독으로는 요구를 만족할 수 없다.
- 모델별 비율 (15개 작업 기준): Fable 5.1 5개(33%) / Opus 5.5 6개(40%) / Sonnet 5.5 4개(27%).
- 권장 진행 순서: 작업 1, 2 (설계와 기술 검증) -> 3, 4, 5, 6 (골격과 보안 기반) -> 7, 8, 9, 10 (조회 기능과 실시간) -> 11, 12, 13 (AI) -> 14, 15.
- 주 담당 모델: **Fable 5.1**. 작업 수로는 Opus가 가장 많지만, 이 프로젝트는 코드가 없는 상태에서 "무엇을 만들지 않을지"를 정하는 설계 판단이 가장 중요하다. 증권사 선택과 실시간 중계 구조, 키 보관 경계, 주문 안전장치, 법적 리스크를 반영한 범위 축소는 한 번 잘못 정하면 이후 작업 전체를 다시 해야 하고 금전 손실로 이어질 수 있다. Fable이 PRD 보강, 스키마/RLS, 키 보관, 시세 워커, 주문 모듈을 맡아 기반을 확정한 뒤, 정의된 연동과 AI 라우트는 Opus, UI와 문서는 Sonnet으로 내려 비용을 줄이는 구성을 권장한다.
