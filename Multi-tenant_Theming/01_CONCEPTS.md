# 01_CONCEPTS — 용어, 커스터마이징 단계, 판매 모델, 원칙

작성일 2026-10-14. 멀티테넌트 테마를 설계·견적·개발할 때 같은 말로 이야기하기 위한 기준 문서다.

## 1. 용어 사전

| 용어 | 정의 | 이 저장소에서의 실체 |
|---|---|---|
| 테넌트(Tenant) | 시스템을 나눠 쓰는 고객 단위 | `core.organizations` 1행. 개인 조직(`is_personal`)도 테넌트지만 화이트라벨 대상은 보통 회사 조직 |
| 멀티테넌시 | 한 시스템이 여러 테넌트를 데이터·설정 단위로 분리해 서비스 | 모든 테넌트 테이블의 `org_id` + RLS(`DB_CONVENTIONS.md` 3·7장) |
| 화이트라벨 | 플랫폼을 고객사 이름·로고·도메인으로 바꿔 고객사가 자기 서비스처럼 쓰거나 재판매 | 공용 판매 모델 B(`Price_Plans/_common/PRICING_PRINCIPLES.md` 5장) |
| 리브랜딩·스키닝 | 화면 겉모습(로고, 색, 서체)만 바꾸는 것 | L1 |
| 테넌트 테마 | 테넌트별 로고·토큰·서체 묶음. 버전이 있다 | `core.tenant_themes` |
| 디자인 토큰 | 디자인 값을 이름 붙은 변수로 관리 | `src/styles/tokens.css`(Tailwind CSS v4 `@theme`) |
| 원시 / 의미 / 컴포넌트 토큰 | 값 자체(blue-600) / 용도(brand) / 부품(button-bg) | 테넌트는 의미 토큰 허용 목록만 바꾼다 |
| 엔타이틀먼트 | 조직이 앱을 어떤 플랜으로 쓸 수 있는가 | `core.app_entitlements` |
| 피처 플래그 | 기능 켜고 끄기·한도 값 | `core.plans.features` + `core.tenant_feature_overrides` |
| 화이트라벨 단계 | 이 문서의 L0~L4. 숫자 하나로 무엇을 바꿀 수 있는지 정한다 | `features.theming_level` |
| 커스텀 도메인 | 고객 소유 도메인으로 접속 | `core.tenant_domains` |
| 서브도메인 | 플랫폼 도메인 아래 `<slug>.` 주소 | 조직 `slug`(행 없음) |
| 슬롯·확장 포인트 | 코드에 미리 뚫어 둔 교체 지점 | `<Slot name>` + `core.tenant_extensions` |
| 포크 | 고객사별로 저장소를 복제해 따로 개발 | 금지(L5) |
| 컨트롤 플레인 | 모든 고객사 배포를 관리하는 운영자 DB·화면 | `core.tenant_deployments` + 운영자 화면 |
| 구축형 / 임대형 | 국내 SI 용어. 고객 서버 설치 / 월 구독 | 모델 A / 모델 C |

## 2. 단계 판단 기준 (요청이 들어오면 이 순서로 묻는다)

| 질문 | 예 | 단계 |
|---|---|---|
| 겉모습(로고·색·서체·파비콘·사업자 정보)만 바꾸나? | "우리 로고와 파란색으로" | L1 |
| 이미 있는 기능·메뉴·용어를 고르거나 이름만 바꾸나? | "회원 대신 수강생", "결제 메뉴 숨김", "우리 도메인으로" | L2 |
| 화면 한 영역을 다르게 보여줘야 하나(데이터와 로직은 같음)? | "대시보드 첫 화면을 우리 KPI 카드로" | L3 |
| 새 로직·외부 연동이 필요한가? | "주문이 생기면 우리 ERP로 전송" | L4 |
| 위 어디에도 안 맞고 구조가 달라지나? | "결제 흐름 전체를 우리 방식으로" | L5 → 거절하거나, 공통 기능으로 만들 가치가 있으면 제품 로드맵에 올리고 모든 고객에게 제공 |

판단 규칙:

- 같은 L3·L4 요청이 **두 고객사**에서 나오면 공통 기능(L2 설정 또는 제품 기능)으로 끌어올린다. `extensions/`가 커지는 것은 사업이 위험해지는 신호다.
- L3 이상은 "코드는 우리 저장소, 켜고 끄기는 DB"다. 고객사 전용 코드도 우리 저장소·우리 CI·우리 테스트를 통과해야 배포된다.
- 고객이 원하는 것이 사실 "데이터 내보내기"면 L4가 아니라 기존 웹훅·CSV로 해결한다(`automation-core`, n8n).

## 3. 판매 모델과의 연결

| 모델 | 정의(`PRICING_PRINCIPLES.md` 5장) | DB 배치 | 테마 적용 방식 | 테넌트 식별 |
|---|---|---|---|---|
| A 설치형 | 1회 + 연간, 고객 API 키, 로컬 저장 | Supabase 없음(로컬 IndexedDB 등) | 빌드 시 넣는 `tenant.json`(해석 결과와 같은 JSON 형식) | 없음(설치본 1개 = 고객 1개) |
| B 호스팅 화이트라벨 | 셋업 + 월 유지보수, 고객별 전용 Supabase | 고객사 전용 프로젝트에 **같은 마이그레이션**, 조직 1개 | DB 해석(이 문서 그대로) | 커스텀 도메인 1개 |
| C 표준 SaaS | 구독 + 크레딧팩, RLS 공유 | 통합(모듈러) 프로젝트, 조직 여러 개 | DB 해석 | 서브도메인 또는 커스텀 도메인(L2) |

- **같은 스키마, 다른 배치**: B와 C의 차이는 "조직이 몇 개 들어 있는 DB인가"뿐이다. C로 시작한 고객사를 B로 옮길 때 코드가 바뀌지 않는다.
- 운영자는 모든 고객사의 배치를 컨트롤 플레인(`core.tenant_deployments`, 운영자 통합 DB)에서 본다. B 고객사 전용 DB 안의 같은 표는 비어 있어도 된다.
- 모델 A는 해석 함수를 부르지 않지만, `packages/core-tenancy`의 같은 타입(`ResolvedTenant`)을 쓰므로 화면 코드는 같다.

## 4. 구조 선택지 비교

| 방식 | 설명 | 초기 비용 | 유지보수 | 확장성 | 고객 10곳일 때 | 판정 |
|---|---|---|---|---|---|---|
| 고객사별 포크 | 저장소 복제 후 수정 | 낮음 | 매우 나쁨(버그 수정 N번) | 나쁨 | 1인 운영 불가 | 금지 |
| 환경변수 테마 | 배포마다 `NEXT_PUBLIC_BRAND_COLOR` 등 | 낮음 | 보통(배포 N개) | 나쁨(배포마다 빌드) | 빌드·배포 10개 | 모델 A 전용으로만 |
| **DB 설정 기반(이 문서)** | 한 배포, 요청마다 테넌트 해석 | 중간(1회) | 좋음 | 좋음 | 배포 1개 + 설정 10개 | **기본값** |
| DB 설정 + 고객사 전용 DB | 위 방식 + 데이터만 물리 분리 | 중간 | 좋음(마이그레이션은 N번 적용) | 좋음 | 배포 1~N개, DB 10개 | 모델 B |
| 마이크로 프론트엔드 | 고객사별 앱 조각 조립 | 높음 | 보통 | 좋음 | 과잉 | 쓰지 않음 |

추천: **DB 설정 기반을 기본으로, 데이터 격리를 요구하는 고객만 모델 B**. 근거는 1인 운영(배포·빌드 1개), 기존 코어(org·RLS·엔타이틀먼트)를 그대로 재사용, 셀프서비스 L1으로 원가 0에 가까운 납품.

## 5. 원칙

| 원칙 | 내용 |
|---|---|
| 코드는 하나 | 고객사별 분기는 `if (tenant === 'acme')`가 아니라 단계·플래그·슬롯으로 한다. 테넌트 slug로 분기하는 코드는 린트로 막는다(03장 7절) |
| 서버가 정본 | 단계·기능·테마 판정은 DB(`theming_level`, `effective_features`, `resolve_tenant`). 클라이언트 값은 표시용 |
| 의미 토큰만 개방 | 배경·본문 글자·상태색(위험·성공·경고)은 플랫폼이 고정한다. 고객 색 때문에 오류 표시가 안 보이는 사고를 막는다 |
| 게시 전 대비 검사 | 대비 검사를 통과한 초안만 게시된다(DB가 강제, TM002) |
| 게시본은 불변 | 고치려면 복제해서 새 초안. 버전 기록이 그대로 되돌리기 기능이 된다 |
| 실패하면 기본 테마 | 해석이 실패해도 서비스는 플랫폼 기본 테마로 계속 동작한다 |
| 셀프서비스 우선 | L1은 고객사 관리자가 직접 한다. 운영자가 손으로 해 주는 작업은 L2 이상 견적에 넣는다 |

## 6. 금지

- 고객사별 저장소 포크, 고객사 slug로 분기하는 코드, 고객사 전용 env 파일.
- 테넌트가 원시 토큰·중립색·상태색을 바꾸는 것, 임의 CSS 문자열·URL·`@import`를 토큰으로 받는 것.
- 로고 SVG를 `dangerouslySetInnerHTML`로 인라인 삽입(`<img>` 또는 정화한 SVG만, 02장 3절).
- 클라이언트에서 테마를 불러와 바꾸는 방식(깜빡임, 첫 화면 브랜드 노출 사고).
- 해석 결과에 비공개 값(확장 `config`, 결제·한도 상세, 멤버 정보)을 넣는 것.
- 게시본을 직접 고치는 것, 대비 결과를 사용자 세션에서 쓰는 것.
- "무제한 커스터마이징" 같은 계약 문구(`PRICING_PRINCIPLES.md` 6장 "무제한 금지").
