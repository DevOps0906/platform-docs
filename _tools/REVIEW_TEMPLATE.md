# 리뷰 작성 가이드 (분석 에이전트용)

출력 파일: `D:\WorkSpace\platform\docs\reviews\<프로젝트명>.md` (한국어, UTF-8)
프로젝트명은 폴더명을 그대로 쓰되 공백은 `_`로 바꿈 (예: `NOMAD_Shorts_Maker.md`).

## 반드시 지킬 것
- 실제 코드를 읽고 쓴다. 추측으로 쓰지 않는다. 문제점은 반드시 `상대경로:줄번호` 로 근거를 단다.
- node_modules, dist, .next, venv, ckpts, __pycache__ 는 읽지 않는다.
- 표는 Markdown 표(`|`)만 사용. HTML 태그 금지. 이미지 금지. 이모지 금지.
- 분량: 프로젝트당 A4 3~6페이지 분량 (코드 규모가 작거나 기획안만 있으면 2~3페이지).

## 모델 배정 기준 (수정 작업마다 반드시 1개 지정)
- **Fable 5.1**: 아키텍처 재설계, 다중 모듈에 걸친 리팩토링, 인증/권한/보안/결제 로직, 데이터 모델 재설계, 원인이 불명확한 복잡한 버그, 기획안만 있는 프로젝트의 설계와 초기 골격 구현, 성능 병목 진단.
- **Opus 5.5**: 명확히 정의된 중간 규모 기능 구현, 2~5개 파일 리팩토링, API 연동, 상태관리 정리, 테스트 설계, 중간 난이도 버그 수정.
- **Sonnet 5.5**: UI/스타일 수정, 문구/다국어, 보일러플레이트 생성, 단순 버그, 린트/타입 오류 정리, 문서화, 반복적 컴포넌트 작업, 설정 파일 정리.
- 원칙: 비용 효율을 위해 가능한 가장 낮은 등급을 쓰되, 실수 시 비용(보안, 데이터, 돈)이 큰 작업은 상위 모델을 쓴다.

## 문서 구조 (이 순서와 제목을 그대로 사용)

# <프로젝트명> 코드 리뷰

## 1. 프로젝트 개요
- 한 줄 설명, 목적/대상 사용자
- 기술 스택 표 (프론트/백엔드/DB/인프라/AI)
- 현재 완성도 추정 (%) 와 근거
- 핵심 기능 목록

## 2. 구조 분석
- 주요 디렉토리/파일과 역할 (표)
- 데이터 흐름 또는 아키텍처 요약 (문장)

## 3. 발견된 문제점
표: | # | 심각도(높음/중간/낮음) | 분류(보안/버그/성능/구조/품질/설정) | 위치(경로:줄) | 내용 |
그 아래 심각도 높음 항목은 각각 2~4문장으로 상세 설명.

## 4. 효율성 개선 제안
- 구조/아키텍처
- 성능
- 개발 생산성 (빌드, 타입, 테스트, 중복 제거)
- 운영/배포

## 5. 수정 작업 목록 및 권장 모델
표: | # | 작업 | 우선순위(P0/P1/P2) | 예상 규모(S/M/L) | 권장 모델 | 선정 이유 |
작업은 8~15개. 각 작업은 바로 실행 가능한 수준으로 구체적으로 쓴다.

## 6. 종합 평가
- 강점 3개, 약점 3개
- 전체 작업 중 모델별 비율 (Fable / Opus / Sonnet 각각 %)
- 권장 진행 순서 (1단계 → 2단계 → 3단계)
- 이 프로젝트에 가장 적합한 "주 담당 모델" 1개와 이유 (한 문단)
